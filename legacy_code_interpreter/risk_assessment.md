# Risk Assessment

Codebase: osCommerce 2.x (legacy PHP e-commerce platform)
Source: https://github.com/osCommerce/oscommerce2

| Risk | Severity | Description | Notes |
|---|---|---|---|
| SQL injection in database queries | High | Attacker-controlled input is concatenated directly into SQL query strings throughout the codebase. Without parameterized queries, a malicious value in a URL or form field can alter query logic, dump the entire database, or destroy data. | Found in catalog pages, admin product management, and search handlers. Functions like `tep_db_query()` wrap the legacy `mysql_query()` API which was removed in PHP 7. No prepared statement abstraction exists anywhere in the core. Immediate remediation requires migrating all queries to PDO or MySQLi with bound parameters. |
| Cross-site scripting in rendered output | High | User-supplied and database-sourced values are echoed into HTML without encoding. A malicious product name or URL parameter that contains `<script>` tags will execute in visitors' browsers, enabling session theft, phishing overlays, or credential harvesting at scale. | Affects product listing pages, order confirmation pages, and error messages. No template engine with auto-escaping is used; raw `echo` and string concatenation dominate view files. All dynamic values must be wrapped in `htmlspecialchars($val, ENT_QUOTES, 'UTF-8')` before output. |
| Session fixation after authentication | High | The session identifier assigned before login is kept unchanged after the user successfully authenticates. An attacker who plants a known session ID (e.g., via a crafted link) retains access to the now-authenticated session without ever knowing the password. | `session_regenerate_id(true)` is absent from the login flow in `includes/application_top.php`. Secure and HttpOnly cookie flags are not enforced in code. The legacy `session_register()` function used here was removed in PHP 5.4, making the application incompatible with modern runtimes. |
| CSRF exposure on state-changing actions | High | Forms that trigger checkout, address changes, and account updates do not include unpredictable per-session tokens. Any page on the internet can silently submit those forms on behalf of a logged-in user, causing unauthorized purchases or account modifications. | The checkout flow in `catalog/checkout_process.php` relies entirely on session state checks without validating request origin. No CSRF middleware or token generation utility exists in the codebase. Remediation requires adding a synchronized token pattern to every form and verifying it server-side. |
| Use of removed or deprecated PHP APIs | High | Core application logic depends on PHP extensions and functions that were officially deprecated and then removed in PHP 7.0–7.2. Running on any modern PHP version causes fatal errors, meaning the codebase cannot be upgraded without a substantial rewrite of data-access and session-handling layers. | Affected functions include `mysql_connect()`, `mysql_query()`, `mysql_real_escape_string()`, `session_register()`, `ereg()`, and `mcrypt_*`. Additionally, the code assumes `register_globals` is enabled, a directive removed in PHP 5.4. All of these represent both a runtime compatibility risk and an active security risk due to missing patches. |
| Inconsistent checkout data integrity | Medium | The checkout process spans stock decrement, order creation, payment capture, and email notification in a single procedural script with no database transaction wrapper. A failure at any mid-point step leaves the system in an inconsistent state — for example, stock is reduced but no order is recorded, or payment is captured but the customer receives no confirmation. | Located in `catalog/checkout_process.php`, a 500+ line script with no rollback capability. No compensating logic exists for partial failures. Fixing this requires wrapping the order creation and stock update in a single atomic database transaction and extracting each responsibility into a dedicated service class. |
| No automated regression test suite | Medium | The entire codebase contains zero unit, integration, or end-to-end tests. Every code change, whether a bug fix or a security patch, is validated only by manual testing or by observing failures in production. This dramatically slows safe development and makes it impossible to confidently refactor high-risk areas. | Affected modules include cart calculations, tax and shipping logic, payment gateway integration, and order management. The flat-file architecture and global variable usage make retrofitting tests difficult. A testing strategy must begin with integration tests at the HTTP boundary before attempting unit-level isolation. |
| Limited observability and incident diagnostics | Medium | Runtime errors are either silently suppressed or printed directly to the browser response. There is no structured logging framework, no centralised error aggregation, and no alerting. When a payment failure or data corruption event occurs, there is no audit trail to determine what happened, when, or which user was affected. | PHP's `display_errors` is effectively relied upon for developer feedback, which also leaks stack traces and file paths to end users in misconfigured environments — an information disclosure risk. Introducing a PSR-3-compatible logger such as Monolog and routing all errors through it would be the minimum viable improvement. |
